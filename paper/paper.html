Abstract

Research Summary

This study asks whether page-level search-performance signals can support the prioritization of content for refresh review. Using the FlyRank ML Internship warehouse and the fact_content_daily_performance table, the analysis frames content-refresh prioritization as a supervised classification problem and compares a leakage-safe Random Forest model with a majority-class baseline on held-out data. Because the target is imbalanced, with approximately 8% of observations belonging to the positive class, the baseline achieves higher raw accuracy (0.919 versus 0.897), while the model provides non-zero precision, recall, and F1 on the minority outcome. The final model achieved precision of 0.194, recall of 0.086, and F1 of 0.120. An earlier exploratory version showed inflated performance because target-defining variables such as gsc_clicks and CTR were used as predictors; those variables were removed in the leakage-safe evaluation. The resulting framework is therefore presented as a reproducible decision-support workflow rather than evidence that a model can guarantee future ranking, traffic, click, or content-refresh improvements.

01 · Question

Introduction & Problem Statement

Content teams often have more pages that could potentially be refreshed than they can review immediately. The operational challenge is therefore not simply determining whether a page is performing well or poorly, but deciding which pages deserve attention first.

This project investigates whether measurable page-level search-performance signals can be transformed into a ranked content-refresh prioritization workflow. The intended use is practical: identify pages for human investigation before editorial resources are allocated.

Research Question:
Can page-level search-performance signals be used to identify content that should be prioritized for refresh before its search visibility deteriorates?

Decision Supported

Which pages should receive review priority based on measurable performance signals?

Analytical Approach

Supervised classification with a simple majority-class reference baseline.

Intended User

Content, SEO, editorial, and analytical teams making review-priority decisions.

03 · Methodology

Research Design

The analysis treats content-refresh prioritization as a supervised classification problem. The objective is not to predict search rankings directly, but to identify pages that warrant review based on observable search-performance signals.

Problem Formulation

The model produces a prioritization signal. It is not designed to estimate the causal effect of refreshing a page and should not be interpreted as a guarantee of future search performance.

Feature Construction

Candidate features represent measurable page-level search-performance signals. Features that directly define the target are removed from the final predictive feature set.

Label Definition

The target used in the final evaluation is the binary indicator gsc_clicks_gt_0, representing whether an observation records a positive GSC click outcome.

This label is treated as a decision-support outcome rather than a ground-truth measure of whether a future content refresh will succeed.

Baseline

A majority-class baseline is retained as the reference approach. Both the baseline and the machine-learning model are evaluated on the same held-out observations.

Validation

The final evaluation uses an unseen held-out evaluation set with an 80/20 stratified split. Stratification preserves the approximate class distribution between training and evaluation data.

Leakage Audit

Leakage was treated as a central methodological risk. In particular, gsc_clicks directly defines the target and therefore cannot serve as a predictive feature. CTR is also excluded because it is derived from click and impression information and consequently contains information directly related to the target.

Leakage-control rule
  • gsc_clicks — excluded because it directly constructs the target.
  • ctr — excluded because it is derived from click information.
  • Client identifiers — excluded for analytical and public-safety reasons.
  • Content identifiers — excluded from the predictive signal.

Model

The leakage-safe model is a Random Forest classifier. The model is evaluated against the majority-class baseline using accuracy, precision, recall, and F1 score.

Interpretation

The target is imbalanced, with approximately 8% of observations belonging to the positive class. Consequently, the majority-class baseline can obtain high raw accuracy simply by predicting the majority outcome.

The baseline therefore achieves higher accuracy than the machine-learning model: 0.919 versus 0.897. However, the baseline does not identify the minority class, while the Random Forest produces non-zero precision, recall, and F1.

Main finding: The leakage-safe model provides a limited minority-class signal, but its current predictive performance is weak. The result supports using the model only as a prioritization aid rather than as an autonomous decision system.

Why Leakage Control Matters

An earlier exploratory model included variables directly related to the target, including gsc_clicks and CTR. This generated inflated performance because the model was effectively given information about the answer it was supposed to predict.

After removing these target-derived variables, the resulting performance became substantially more modest. This is an important research finding: an impressive score is not useful if the evaluation design allows the model to access information that would not legitimately be available at prediction time.

05 · Limitations

Limitations & Honest Framing

The findings should be interpreted conservatively. This is a decision-support study, not a causal experiment.

  • The target is a decision-support label rather than a directly observed future business outcome.
  • The analysis does not establish that refreshing a page causes improved rankings, clicks, or traffic.
  • The results are based on the available FlyRank internship dataset and should not automatically be generalized to every website, industry, or future reporting period.
  • Model performance depends on feature selection, label definition, class imbalance, and validation design.
  • The current recall of 0.086 indicates that the model captures only a limited portion of positive cases.
  • The precision of 0.194 means that many model-flagged observations would still require human investigation before action.
  • Observational search-performance data cannot establish causal relationships without a stronger experimental or quasi-experimental design.
Strongest defensible claim: This analysis provides a reproducible, data-informed framework for prioritizing content for human review. It does not demonstrate that the model can guarantee future search-performance improvements.
06 · Recommendations

Ranked Content-Refresh Playbook

The analytical output should be translated into an accountable editorial workflow rather than an automatic content-editing system.

01

Review the highest-priority pages first

Use the strongest available prioritization signals to create an initial review queue. A high score should identify a page for investigation rather than automatically trigger a rewrite.

02

Investigate sustained performance declines

Distinguish persistent deterioration from short-term fluctuations by reviewing recent performance against an appropriate historical period.

03

Prioritize actionable opportunities

Give greater operational attention to pages where diagnosis suggests a specific intervention, such as outdated information, weak intent alignment, incomplete coverage, or unclear content structure.

04

Require human review

The model is a prioritization mechanism, not an autonomous content editor. Human reviewers should validate the recommendation and determine the appropriate intervention.

05

Measure performance after refresh

After an update, monitor subsequent performance against an appropriate pre-refresh period while avoiding unsupported causal claims.

Operating sequence:
Detect → Diagnose → Prioritize → Human Review → Refresh → Measure
